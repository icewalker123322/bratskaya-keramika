# Администрирование «Братской керамики»

Текущий проект уже подключён: база и исходный контент установлены, владелец создан с логином `glinamaster`. Не выполняйте первоначальную установку повторно. Пароль задан отдельно и в репозитории не хранится. Вход и операции с текстовым контентом проверены через реальный API. Хранилище фотографий требует отдельной настройки и проверки загрузки.

Сайт остаётся статическим: HTML, CSS и JavaScript, без сборки и собственного сервера. Панель находится в `admin/index.html` и открывается по `/admin/`. Контент хранится в Supabase Postgres, вход — Supabase Auth, загруженные фото — Storage. До настройки и при недоступности Supabase посетителям показывается исходный HTML. Без JavaScript также доступна исходная версия. Динамические изменения SEO учитываются не всеми поисковыми роботами: исходные title и description сохранены; для гарантированной индексации обновлений потребуется отдельная генерация HTML при публикации.

## 1. Создать Supabase

Создайте проект на https://supabase.com/dashboard и дождитесь его готовности. Сохраните пароль БД отдельно: в сайт он не вставляется. В настройках проекта / API Keys найдите **Publishable key** (`sb_publishable_...`), а в Connect / Data API — **Project URL** вида `https://PROJECT.supabase.co`.

В `cms-config.js` заполните только эти два публичных значения:

```js
window.CMS_CONFIG = Object.freeze({
  url: 'https://PROJECT.supabase.co',
  publishableKey: 'sb_publishable_...'
});
```

Это пример формата, а не рабочие реквизиты. Secret key и service_role запрещены в браузере. Библиотека Supabase JS закреплена на версии 2.49.1 и загружается с esm.sh; доступ к этому домену нужен для работы CMS. Исходный сайт от CDN не зависит.

## 2. Таблицы, RLS и Storage

В SQL Editor выполните **сначала `supabase/schema.sql`, затем `supabase/seed.sql`**. Schema рассчитана на однократную установку в новый проект. Не запускайте её повторно поверх работающей схемы. Seed можно повторить: `ON CONFLICT DO NOTHING` сохраняет правки. Перед изменениями схемы работающего проекта делайте резервную копию.

Seed содержит реальный исходный контент сайта. Без записи `settings` CMS считает импорт незавершённым и оставляет исходную страницу. Не удаляйте служебные записи вручную.

Schema создаёт:

- `site_admins`: пользователь читает только собственное членство; добавление администраторов доступно только через доверенную консоль SQL.
- `site_content`: посетители читают только опубликованные записи; изменения разрешены только членам `site_admins`. Удалять через клиент можно только карточки, FAQ, преимущества и работы галереи.
- RPC `move_site_content`: атомарная перестановка соседних элементов с проверкой администратора.
- Публичный bucket `site-images`: лимит 5 МБ, MIME JPG/PNG/WebP, загрузка и удаление только администраторами. Перезапись файлов запрещена, замена создаёт новый URL. Удаление используемого фото блокируется политикой БД, включая ссылки из скрытых элементов.

Публичный bucket необходим для просмотра фото без входа. Скрытие карточки закрывает её текст от публичного API, но **не делает уже известный URL фотографии секретным**. Не загружайте конфиденциальные файлы. Клиент проверяет MIME, сигнатуру, декодирование и разрешение изображения. Storage дополнительно проверяет MIME и размер, но не заменяет серверную антивирусную проверку. SVG, HTML и скрипты интерфейс не принимает; фотографии выводятся только через `img`.

Проверьте Storage / site-images: Public включён, File size limit 5 MB, MIME types `image/jpeg,image/png,image/webp`. Не добавляйте широкие политики, разрешающие запись всем authenticated: обычный вошедший пользователь не является администратором.

## 3. Первый владелец

В панели сайта вход выполняется по логину `glinamaster` и паролю. Личная почта не требуется: внутри Supabase Auth логину соответствует технический идентификатор `owner@bratsk-ceramics.invalid`. Это не почтовый ящик, письма на него не отправляются. Соответствие задано в `admin/auth-config.js`; пароль там не хранится.

В Authentication / Providers / Email отключите **Allow new users to sign up** (публичную регистрацию). В Authentication / Users → Add user → Create new user создайте пользователя `owner@bratsk-ceramics.invalid` с сильным паролем и включите **Auto Confirm User**. Не используйте Invite user: технический адрес не принимает письма. В SQL Editor выполните:

```sql
insert into public.site_admins(user_id)
select id from auth.users where email = 'owner@bratsk-ceramics.invalid'
on conflict do nothing;
```

Проверьте, что вставлена одна строка. Панель не содержит регистрации, выдачи прав или сброса пароля. Пароль можно сменить через доверенную консоль Supabase. Для отзыва прав удалите строку из `site_admins`: RLS блокирует последующие изменения даже при открытой панели.

В Auth / URL Configuration укажите HTTPS-адрес сайта как Site URL. Для входа по паролю redirect не требуется. Настройте ограничения частоты входа в Supabase Auth. Сессия панели хранится в sessionStorage текущей вкладки, выход завершает сессию. На общем компьютере всегда нажимайте «Выйти».

## 4. Размещение

Загрузите в корень статического хостинга `index.html`, `app.js`, существующие CSS и `assets/`, все `cms-*.js`, каталог `admin/`. Не публикуйте тестовые артефакты, SQL и документацию, если они не нужны на хостинге; SQL не содержит ключей, но для работы браузера не требуется. На Netlify/Vercel оставьте build command пустой, publish/output directory — каталог сайта. На GitHub Pages опубликуйте содержимое этой папки. Все пути относительные: для project Pages панель будет по `/REPO/admin/`.

Не добавляйте SPA-перенаправление всех путей на главную: `/admin/` обслуживает собственный `index.html`. После обновления `cms-config.js` сбросьте кэш хостинга. Не кэшируйте этот файл надолго. Используйте HTTPS. Локально открывайте через HTTP, а не `file://`, например `python -m http.server 8080` из папки сайта.

## 5. Использование

Откройте `/admin/`, войдите по логину `glinamaster` и паролю владельца. «Страницы» содержит все текстовые фрагменты, ссылки контактов, фотографии секций, карточки и FAQ. Заголовки с выделением и переносами разделены на фрагменты, чтобы сохранить оформление. Поиск и фильтр разделов помогают найти нужный текст. Тексты сохраняются как обычный текст, HTML не исполняется.

Карточки, работы, преимущества и вопросы можно добавлять, скрывать, публиковать, переставлять стрелками и удалять с подтверждением. Новый элемент изначально скрыт. «Фотографии» загружает файлы в библиотеку; затем выберите фото в форме нужного элемента. Загрузка в библиотеку сама по себе не добавляет работу в галерею: создайте работу и выберите фото. Заменить фото секции можно в её записи типа «Фотографии». Исходные файлы assets не удаляются панелью, но их можно заменить на странице. Удалять загруженный файл можно после замены всех его использований. Предел текущей библиотеки — 1000 файлов.

«Настройки» изменяет название вкладки и meta description после динамической загрузки. Сохранение сразу публикует правки существующих опубликованных элементов; отдельной системы черновиков текстов нет. Посетителям достаточно обновить страницу. При одновременном редактировании одной записи проверяется `updated_at`, и устаревшая форма не перезаписывает новую версию.

## 6. Проверка на вашем проекте

После подключения выполните проверки на тестовом контенте:

1. В приватном окне `/admin/` показывает вход; неверный пароль не открывает панель.
2. Пользователь Auth без строки в `site_admins` не получает доступ. Прямой запрос INSERT/UPDATE/DELETE к `site_content` от anon и обычного authenticated отклоняется RLS; то же для Storage.
3. Владелец меняет текст, перезагружает публичную страницу и видит изменение. Возвратите текст после проверки.
4. Добавьте скрытую работу: публичный API не возвращает её. Опубликуйте, переставьте, проверьте фильтр и просмотр фото, скройте и удалите.
5. Загрузите JPG/PNG/WebP, замените фото и проверьте публичную страницу. Файл больше 5 МБ и HTML/SVG должны отклоняться. Удаление используемого изображения должно блокироваться.
6. Введите `<img src=x onerror=alert(1)>` в текст: сайт должен показать строку без выполнения кода. Ссылка `javascript:` должна отклоняться формой.
7. Проверьте страницу и панель на ширине 390 px, выход, повторный вход и отозванные права владельца.
8. Заблокируйте доступ к Supabase: исходная версия сайта должна оставаться доступной, ошибки операций панели должны быть видны пользователю.

Сведения по использованным API и политикам: [Supabase Auth](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [защита данных](https://supabase.com/docs/guides/database/secure-data), [Storage RLS](https://supabase.com/docs/guides/storage/security/access-control).

Живая авторизация, применение SQL, RLS, загрузка файлов и сохранение в вашем проекте требуют ваших реквизитов Supabase и не считаются проверенными одними локальными тестами.
